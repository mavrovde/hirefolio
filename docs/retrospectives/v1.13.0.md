## 1. Acceptance criteria

**No AC was unachievable this time.** v1.12.0's headline AC defect (#277's mutation-pin over two
observably identical code states) did not recur; `issue-author`'s charter gained that rule at
v1.12.0 and the six issues shipped here (#248, #262, #263, #271, #288, plus #247's remaining phases)
carry criteria that were all, in the end, checkable.

**But one AC was MET AS WRITTEN AND UNMET AS INTENDED — a new shape.** #288's AC2 read
`grep -rn 'mavrov' --include='*.yml' --include='*.py'` → "returns only the domain and the repo path".
The author ran it and reported 0 bare database names, truthfully. Both of #299's round-1 blockers
lived in `.mcp.json:8` and `backend/.env.example:10` — file types the filter excluded — and one of
them is *the file a bare-metal forker copies*. The reviewer's verdict names the mechanism exactly:

> "It escaped AC2's grep only because the grep was `--include='*.yml' --include='*.py'`."

and then, granting the criterion: *"**MET as literally written** … Note the criterion's grep is
narrower than its intent."* An AC whose verification is narrower than its claim is an AC written to
be closed rather than to be true. → `issue-author` charter.

**`Closes` against unmet criteria: zero.** v1.12.0 had five occurrences in four PRs; this release
none — every feature PR used `Refs #NN` and ticked the boxes at close-the-loop. The `pre-merge-gate`
hook shipped in #291 during this window and, more importantly, the convention it enforces is now
visible in the PR bodies. One reviewer note remains valid: `Refs` must not become the way *past* the
gate (#299 finding 10) — it wasn't, but say why you chose it.

**Silently-skipped criteria still happen, and review still catches them all**: #289 (#247 criterion
3's SMTP-reminder clause absent from diff, body and CHANGELOG), #294 (variant upload silently
deactivated the public CV — criterion clause 2 failed end-to-end), #290 (`Closes #276` while all
three of its boxes were unticked). Six such findings across 16 PRs, versus six across 10 in v1.12.0
— proportionally better, not solved.

## 2. Issue quality

**Grounding held.** Across 50 verdicts there is again **no finding of the form "the issue cited
something that isn't there"**. #248, #262 and #263 were implemented straight from their bodies.

**Close-the-loop quality is the clearest improvement of the release.** Every shipped issue closed
with a comment naming the PR, the merge SHA, the pipeline run id, the independent verdict, and each
criterion with what was run for it — e.g. #288's names run `34087345743`, the round-2 APPROVE at
`7086ed9`, and per-criterion evidence including the reviewer's widened grep. That is exactly what
rule 7 asks for and it was inconsistent a release ago.

**The one issue-side defect is a doc-not-issue one:** #299 found the *charters* stale (`backend-dev.md`
still said `docker exec mavrovde-db-1 … CREATE DATABASE mavrov_fix`, a container that no longer
exists and a name the conftest guard would refuse). Instruction files drift like code and nothing
greps them. Noted for the drift-check follow-up (#232/#246).

### The three that earned config changes

**(1) Class A — "the container never receives the variable", three times in one release.**
Neither compose file uses `env_file:`; each service carries an explicit `environment:` allowlist, and
`app/config.py`'s own `env_file=".env"` resolves *inside* the container. So a fully implemented,
fully documented feature is inert:

| PR | The promise | The measurement |
|---|---|---|
| #296 | prod `--profile mail` + `SMTP_*` | `docker compose -f docker-compose.prod.yml config` → backend has 35 env keys, **none** SMTP/MAIL |
| #297 | `setup.sh:150` + `README.md:509`: set `HIREFOLIO_TELEGRAM_BOT_TOKEN`… | `TELEGRAM present: []  NOTIFY present: []  env_file: None` |
| #298 | `.env.example:190-195`: `TRANSLATION_ENABLED=false` | `docker exec … env \| grep -c` → **0**; AC5 undeliverable |

with #256 (`ADMIN_PASSWORD`) and #228 (`LINKEDIN_IMPORT_TOKEN`) as priors the repo had already
written inline comments about. Five occurrences, two of them producing shipped-but-inert features.

**(2) Class D — the dead-code chain, #297 rounds 2–4.** A rule-10 settings scrub was inserted into
`backend/conftest.py` behind an idempotency guard that searched the file for the function's own
name — which its `def` line contained. The guard always matched, the call was never written:

> `$ git grep -n "_scrub_notification_settings"` → `backend/conftest.py:50:def _scrub_notification_settings() -> None:` — "One hit in the whole tree: the `def` line."

Three things hid it: coverage cannot see `conftest.py` (`--cov=app`), the suite is green either way
(every channel swallows its exception), and the author's "verification" **called the function by
hand** instead of observing the wire. The reviewer's check was one number — real `httpx.post`
attempts: **20** with the call disabled, **0** with it wired, `30 passed` both ways.

**(3) Class C — the verification's scope.** #299's grep filter, #296's compose base
(`run_integration_tests.sh` layers the DEV compose; CI layers PROD, so a local "21 passed" meant a
red `main` on push), and #297's coverage blind spot are one defect wearing three costumes: *the
instrument was narrower than the claim it backed, and nobody widened it once.*

## 4. Review actions

**Every reviewer catch in this release came from RUNNING something.** Not one blocker was found by
reading a diff. The repertoire, worth copying: two-session `asyncio.Barrier` repros (#284), served-
bundle mutations in a real browser (#282, #290), a four-timezone matrix (#292), socket-level probes
for `generativelanguage.googleapis.com` (#298), a throwaway `pgvector` container to check a Postgres
volume-init claim (#299), `docker compose config` rendered both ways (#296/#297/#299), and — the
release's signature move — **counting real outbound HTTP attempts** instead of trusting a green suite.

**What repeated, and therefore belongs on the author side:**

1. **"Prove the fix by an observable, in both states."** #297 needed three rounds because each round
   fixed an *instance* of the leak (env → dotenv → dead call) while the reviewer asked three times
   for the guard that closes the *class*. Landed in the playbook + lessons §41.
2. **"Widen your instrument once before reporting green."** #299, #296, #297. Landed as lessons §42
   and, for criteria, in `issue-author`.
3. **"A documented knob must reach the container."** #296/#297/#298. Now a lint, not a sentence.
4. **"Rebase before you ask for the merge."** Four class-J findings; the reviewer had to re-verify on
   merged trees twice.

**Rounds that found nothing: zero.** Every one of the 33 REQUEST CHANGES verdicts carried at least
one blocker or major that the reviewer had reproduced. That is the single most important number in
this retro: **the rounds are not churn.** (§5 develops the consequence.)

**A gate defect the review data itself exposed.** `pre-merge-gate.sh` selected "the newest body
containing a verdict marker". On #291, two of those bodies are the AUTHOR's fix reports —
`## Round 4 — the three blockers, each measured against the unfixed hook` and `## Round 7 — blocker
and all four majors closed` — whose first marker is `APPROVED`/`APPROVE`. Reviewer and author post
under the same GitHub identity here, so **no author filter can separate them**; either comment was
"the newest verdict" the moment it was posted, and a merge attempted then would have been **allowed
while the standing verdict was REQUEST CHANGES**. Fixed by position, with a failing-first case.

**A SECOND false-allow, found by this PR's reviewer rather than its author — and worth recording as
the more interesting one.** Replaying every #293 body through both filters, the old gate also
allowed after the second `## ⛔ REJECTED`: that body carries **no marker in its heading** and exactly
one anywhere — the prose *"Ping me on the new head; I will re-run the mutation and the suite and
expect to approve immediately"* (line 108) — which the old case-insensitive body-wide match read as
the verdict. So one matcher produced two independent false-allows on two unrelated threads, which is
the tell that the defect was the **rule**, not any reviewer's wording. It also means the author of
this retrospective found one of the two and the reviewer of the fix found the other: the review gate
caught a gap in the change that closes the review gate. The case is now pinned (it fails against the
pre-change hook), and the legacy `⛔ REJECTED` heading now fails **closed**.

**And the residual, stated because a gate whose limit is unwritten gets trusted past it.** The
heading rule cannot distinguish a fix report whose *first line itself* carries a marker. **This is
the repo's own habit, not a hypothetical** — and the sentence that first stood here ("a shape nobody
has posted") was **false**, caught by this PR's own reviewer in round 2 and then quantified by a
sweep of all **145 merged PRs** (179 marker-bearing headings across 92 of them):

| PR | The author's first line | Posted after |
|---|---|---|
| **#281** (2026-09-06) | ``Round-1 APPROVE findings applied on `1abb0fe` (wording only…)`` | the reviewer's `## ✅ APPROVED`, 6 min earlier |
| **#181** (2026-08-30) | `Approved-with-findings applied before merge:` | the reviewer's `**✅ APPROVED** — …`, 2 min earlier |

Both were **decision-neutral** — the standing verdict was itself APPROVE — so no false-allow has
happened; flip the standing verdict and the same sentence allows a merge against REQUEST CHANGES.
Worth recording as this retrospective's *third* §42 instance, and the sharpest: the corpus behind
"nobody has posted" was the seven threads of this release, and the claim was written repo-wide.

It stays unpinned anyway, and now for a measured reason: no lexical rule separates it from a **real
reviewer heading that also puts prose before the marker** — `## Round 3 — ✅ APPROVED` and
`## Round 2 — ⛔ REJECTED (…)` (#255), `PR-REVIEWER VERDICT: APPROVE` (#171); the first is already
pinned as a test case. (The example first cited here, `## ⛔ REQUEST CHANGES — round 5 (3a6d7bb)`,
put its prose *after* the marker and so did not demonstrate the point at all.) Tightening buys the
residual at the price of rejecting those three, so the **guard is the convention** — `pr-reviewer.md`
and the playbook both require `## Round N — what changed` — and the limit is written into the hook
and lessons §43. Deliberately **not** pinned: a case asserting the residual cannot fail against any
hook that has it (the #240 answer). **Revisit trigger, restated honestly:** not "an actual bad
merge" — the shape exists, so that bar waits for the incident — but **the first fix report with a
leading marker posted while the standing verdict is NEGATIVE**, which is the decision-changing case.

## 5. Cost

**Effort telemetry: ABSENT, and that is the finding.** GitHub Project 3's `Tokens (k)` and
`Time of processing (min)` fields are **empty for every item in the repository**, and `Review rounds`
is unset for all six issues shipped in this release (#248, #262, #263, #271, #288, #276). v1.12.0's
"9.07M tokens / 28.1h" figures came from console session estimates, not from these fields. Rather
than invent comparable numbers, this retro reports what GitHub actually holds:

| Measure | v1.12.0 | v1.13.0 | Direction |
|---|---|---|---|
| PRs merged | 10 | **16** | +60% |
| Reviewer verdicts (canonical-heading) | not comparable¹ | **50** | — |
| Verdict-matching bodies (loose matcher) | 24 | **52** | +117% |
| Mean rounds per PR | 2.4 | **3.13** (loose matcher: 3.25) | **worse** |
| Approved on round 1 | 20% (2/10) | **0% (0/16)** | **worse** |
| REQUEST CHANGES verdicts | 14 | **33** | — |
| Rework share *of verdicts* (rounds 2+) | 58% | **68%** | worse |
| Median changed files per PR | 17 | **14** | smaller |
| Release wall clock (tag→tag) | — | **23.5 h** | — |
| Sum of PR open→merge time | — | **36.1 h** (mean 135 min; PRs overlapped) | — |

¹ v1.12.0's verdict formats predate the mandated heading, so a heading-anchored re-count of that
window returns 15 — an undercount caused by format drift, not a comparison. From v1.13.0 the heading
form is charter-mandated *and* gate-enforced, so this column becomes exact and primary at v1.14.0.

**How the true number was found, because it is the retro's own instance of class C.** The 50 came
from *widening the instrument once* — the rule this release taught (§3, lessons §42). Sweeping every
body whose first line matched **neither** marker turned up exactly one class of miss: #293's two
`## ⛔ REJECTED` verdicts. That single heading did three kinds of damage at once: the merge gate
could not read it, the telemetry lost two real review rounds, and **#293 read as this release's only
round-1 approval when it in fact took three rounds** — so the honest round-1 figure is **0 of 16**,
not 1. `pr-reviewer.md` had prescribed `⛔ REJECTED` since before v1.12.0; it now prescribes the two
canonical headings the gate and the counter both read (change 4).

**Where the cost went.** #291 alone accounts for 8 of 50 verdicts (16%) — the charter/hook PR that
built the merge gate, where round 5 introduced a regression the author found and round 8 blocked on
a three-file conflict. Excluding it: 42 verdicts over 15 PRs = **2.80 mean**, still above v1.12.0.
The three security-shaped feature PRs (#296, #297, #298) cost 4 rounds each — 12 verdicts, 24% of the
release — and the release PR itself cost 3.

**The honest reading, and it contradicts the standing falsification test.** v1.12.0 predicted that if
rounds stayed high while claim-discipline improved, the bottleneck would be PR size. **Median PR size
went DOWN (17 → 14) and rounds went UP.** So size is not the driver. Two things are:

- **The work changed.** v1.13.0 shipped notification channels, bundled mail, and LLM translation —
  three features whose failure modes are *credential leakage, billable outbound calls and container
  configuration*. Class B and Class A barely existed in v1.12.0's corpus and produced 9 blockers here.
- **The reviews are catching real defects, not churning.** Zero empty rounds; every REQUEST CHANGES
  reproduced a defect. A 4-round PR that ends with a bot token no longer printed to `docker logs`,
  20 live credential-bearing requests reduced to 0, and a `1-in-9` CI flake closed at the await
  boundary is **not** a process failure — it is the gate doing its job on harder material.

The right target is therefore **not "fewer rounds"** — it is **"the same defects, found one layer
earlier."** Each of this release's top three classes is now checkable before a reviewer is involved:
a lint (A), a stated observable (D), a widened instrument (C).

## 📌 Prediction (checkable at the v1.14 retro)

Stated as observables, with the instrument named, because the last one was checked and failed:

1. **Zero class-A findings** ("a documented knob does not reach the container") in v1.14.0's review
   corpus. The lint now fails the pre-push gate and CI, so any occurrence means the lint's contract
   is too narrow — and the retro should widen it rather than re-teach the lesson.
2. **Zero merges on a stale approval.** Instrument: for every merged PR, the newest heading-anchored
   verdict at merge time is an APPROVE. (Today's gate makes the #291 false-allow impossible; this
   checks it in production.)
3. **Round-1 approvals ≥ 20%** (v1.13.0: **0%**, 0/16; v1.12.0: 20%). Deliberately set at v1.12.0's level,
   not the 40% that just failed — the diagnosis is that harder material, not author sloppiness, drove
   the rise, so the honest target is "recover the previous rate on harder work".
4. **Mean rounds ≤ 2.8**, canonical-heading (v1.13.0: 3.13; 2.80 excluding #291).

**Falsification stated up front:** if classes A, C and D go to zero while mean rounds stay ≥ 3.0,
then author-side discipline was never the constraint and the next retro should stop editing charters
and look at *reviewer scope* instead — specifically whether a single reviewer serialising 4 rounds
on security-shaped PRs is the actual queue.
