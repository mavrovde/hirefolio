## 1. Acceptance criteria — were they checkable, and were they checked?

**The `Closes`/`Refs` contract held completely.** Every PR with an unmet criterion used `Refs` and
said which criterion and why: #322 (`Refs #252`, the sitemap-link sub-item), #323 (`Refs #250`, AC4's
dashboard half), #325 (`Refs #249`, the deliberate `link_visit`/bookings/referrer exclusions), #312
and #318 likewise. **Zero `Closes` against an unticked box** — the class that was a blocker in four
v1.12.0 PRs. The merge gate's check 2 was never the thing that caught it; the charters were.

**But one AC shape recurred, and it is the one v1.13.0 already wrote a rule for.** A criterion that
names its own verification instrument is only as strong as that instrument, and twice this cycle the
instrument was narrower than the claim it certified:

| Issue | Criterion | What the instrument actually proved |
|---|---|---|
| **#252 AC2** | "`resume.json` **validates against the JSON Resume schema**" | `assert_valid` used `Draft4Validator.FORMAT_CHECKER`, which the reviewer measured to contain exactly `['email','idn-email','ipv4','ipv6','regex']` — **no `date`, no `uri`**. Both shipped demo personas violated `format: date` (`['certificates',0,'date']: '2024' is not a 'date'`), reproduced against the upstream v1.0.0 schema on the served document. The AC read MET and was not. |
| **#313 AC4** | "`check_no_pii.sh`'s exclusion stance updated to match, **self-check green**" | The self-check was green (23 cases) and the guard could not gate: its exemption markers were the bare English words `canonical`/`historical` matched against the whole `git grep` line, and the reviewer re-branded three lines — including a straight revert of a line the PR had just fixed — with `rc=0`. |

That is the third instance of the class (v1.13.0's #288 AC2 was the first: a criterion embedding a
`grep --include='*.yml' --include='*.py'` whose filter hid both of #299's blockers). `issue-author`'s
charter gained *"a criterion that embeds a command embeds its SCOPE"* at v1.13.0 and it recurred, so
the charter is extended rather than repeated — §7, change 8.

**One AC spanned two issues and was correctly reported as half-met**: #250's AC4 asks for visits on
the timeline *and in the engagement dashboard*, and the dashboard is #249's deliverable. Both PRs
reported it honestly (`grep -rni "engagementevent|engagement" backend/app frontend/projects/admin/src`
→ empty, confirmed by the reviewer). Not a defect — but an AC that cannot be satisfied by the PR that
owns it should say so when it is written.

Two of these are new to this repo's record and both are *observation-point* failures rather than
missing tests:

- **#322's PII test** asserted on the mapper's OUTPUT. Deleting the projection changed nothing
  observable there, because `build_json_resume` reads a fixed key set that happens to be a subset of
  the allowlist. Assert at the SEAM — the dict the mapper RECEIVES — and the same mutation gives
  `1 failed, 94 passed` naming `phone`, `birthday`, `connections`, `contact.address`. (lessons §49)
- **#325's CSS assertion** would have gone in the unit suite, where it could not fail: with both
  `border: 1px solid currentColor` rules deleted the admin suite reported `447 passed (447)`, because
  **jsdom never applies the component stylesheet**. Moved to the browser, the same deletion fails on
  all three attempts. (lessons §51)

And one that only exists because of parallelism: **#323 and #325 both set
`down_revision = "trans0009"`**. Each branch was single-head in isolation, so `alembic heads`, the
Backend Migrations drift guard and both full suites were green on both. Measured by the #325 reviewer
on the merged tree:

```
$ alembic heads
engage0010 (head)
tailored0010 (head)
$ alembic upgrade head
FAILED: Multiple head revisions are present for given argument 'head'
```

`backend/docker-entrypoint.sh` runs `alembic upgrade head` on **every** container start, on both the
FRESH and the ALEMBIC_MANAGED path — so this was a production backend that would never have finished
booting, and no automated signal existed anywhere: **GitHub does not re-run a PR's checks when its
base moves**, so #325's green run predated #323's merge entirely. This is the release's clearest
"a gate could catch it mechanically", and §7 change 1 is that gate.

## 4. Review actions — what reviewers caught that authors missed

**Reviewers verified by RUNNING, in every PR.** #322's reviewer ran six independent mutations,
#323's ran six (two the author had not), #325's ran six to eight plus a concurrency sweep to 50-way
that the PR never asked for — which is how #326 was found. Two reviewer catches were of the author's
*fix*, not the original code (#322 minor 6's round-1 fix was measured on the wrong URL path; #312's
round-2 justification was falsified by widening the corpus), which is the shape §42 exists for.

**What repeated, and it is the same thing v1.13.0 named:** a reported number that does not reproduce
— **5 findings across 4 PRs**, all at minor level this time (down from blocker level in v1.12.0):

| PR | Reported | Measured | Why it was wrong |
|---|---|---|---|
| #312 | "8 new cases" | 7 (then genuinely 8 again, for a new reason) | counted against the wrong baseline |
| #318 r1 | AC1 baseline **38** | **37** | counted on a **dirty worktree** (an untracked `settings.local.json`) |
| #318 r1 | "mutation 1 fails **2** cases" | **7** | a **partial run** reported as the suite |
| #318 r2 | six mutation rows | four off by one | the matrix was measured on a **pre-final** version of the suite it described |
| #317 | "49 posts" | corrected in round 2 | — |

The common factor is not staleness: it is **a number quoted without the conditions that produced
it**. `/prep-pr` step 7 already says "re-measure every number" and was followed; it did not ask for
the tree state or the exact invocation. That is the edit (§7, change 7).

**A second repeated catch is new, and it is about parallelism**: three separate times a reviewer had
to work out the *merge order* between two open PRs — #322↔#323 (`sitemap.ts`/`buildRobotsTxt`
signature), #314↔#315 (both adding a `## 44.` to `lessons-learned`), and #323↔#325 (the Alembic
fork). Two were flagged pre-emptively by the reviewer and cost nothing; the third was a blocker. The
reviewer charter now asks for the merge order explicitly whenever two open PRs touch the same ordered
structure (§7, change 5).

**Did any round find nothing?** No. All 9 negative verdicts reproduced a defect, and both round-1
approvals (#315, #320) still carried minors that were fixed in-PR. As at v1.13.0, the rounds are the
gate working, not churn.

**The thing no reviewer caught, because no instrument looked for it — and it is the headline of this
retro.** Replaying every merged PR's thread *as it stood at merge time* through the merge gate:

```
#312 ALLOW   #314 DENY   #315 DENY   #317 ALLOW   #318 ALLOW
#320 DENY    #322 ALLOW  #323 ALLOW  #325 ALLOW   #327 DENY
```

**Four of the ten reviewed merges carried commits that no approval had seen** — including the
release PR itself:

- **#320** — its only verdict was `## ✅ APPROVED — round 1` at 06:57:04Z on `b91f908`. Then
  `0537a86` (the fixes to the reviewer's own five findings — an unbounded auto-fit loop that hangs
  forever, an unvalidated font cache, a padding bug), `54158e8` (a merge of `main`), `e6373a4`
  (*"banner links to the repository, not the maintainer's site"* — a behaviour change) and `8290bca`
  landed. Merged 07:43:35Z. **No second verdict.**
- **#315** — approved 13:40:54Z; the six-finding fix commit `2a7c1a0` landed 13:45:03Z; merged
  14:03:18Z, **two seconds before** the reviewer's `## ✅ APPROVE — round 2 (delta-confirm at
  2a7c1a0)` was posted at 14:03:20Z.
- **#314** — approved 14:00:11Z; `be1ffc2` (a merge of `main` plus a lessons renumber) landed
  14:12:38Z; merged 14:17:58Z.
- **#327, the release PR** — approved 12:09:07Z; `882ddae` (a CHANGELOG wording change the verdict
  itself had suggested) landed 12:10:52Z; merged 12:25:17Z. The tag `v1.14.0` therefore sits on a
  commit no verdict covers. Harmless in substance — it is one sentence of prose — and exactly why
  the rule has to be mechanical rather than a judgement call about which commits "count".

Rule 13 asks for a verdict on the **change**. The gate asked only whether the newest verdict says
APPROVE — a question an approval of a head that no longer exists answers just as well. And "it was
only a merge of `main`" is not a mitigation: that is precisely how #325's Alembic fork appeared.

**And one PR was merged with no verdict at all.** **#321** (Dependabot, `alembic 1.19.1 → 1.19.2`)
was opened 07:07:04Z and merged 07:12:32Z by the maintainer — **5 minutes 28 seconds, zero reviews,
zero comments**. Rule 13 has no carve-out for dependency bumps and says so twice. The merge gate
could not have helped: it is a PreToolUse hook on `gh pr merge`, and this merge came from the web UI.
That is a coverage limit worth stating plainly rather than papering over — see §7's non-changes.

Mean rounds fell by 42% while median PR size *rose* 14 → 20 files — so the fall is not "smaller
PRs". Over the 10 PRs that were actually reviewed the mean is 2.00 and the rework share 50%; #321

28` minutes; the two long tails (#318's 662, #323's 1339) are both branches that sat while another PR
merged ahead of them — the parallelism cost showing up as latency.

**The largest single cost of the cycle was not in any of these columns.** Parallel agents each
composed their own Docker project (`hirefolio-*`, `hirefolio250-*`, `mavrovde-*` at once); the disk
reached zero, the daemon crashed, and the harness could no longer write command output — so the
session that caused it could not see it. Recovery took **~2 hours across two sessions**, and #322's
round-1 fix report shipped with its backend gates explicitly declared **unmeasured**. Measured on
this machine on 2026-09-09, ONE stack of this project is **15.35 GB of images + 3.09 GB of build
cache + 6.97 GB of volumes**; a second does not fit beside it. Two further parallelism costs the same
week: two agents shared one checkout, so #317's branch briefly carried #318's commit and a later
agent had the branch switched under it mid-run; and a `git checkout`/`git stash` during a mutation
loop discarded uncommitted fixes — **the §36 shape, recurring**, which falsifies v1.13.0's decision
to leave it to discipline.

**The shared-checkout failure recurred DURING this retrospective**, which is as direct a datapoint as
the series is likely to get: the retro branch was created off `origin/main`, and by the time the work
was committed `HEAD` was on `main`, so the commit landed there and had to be relocated with
`git branch -f`. One `git push` from that state would have gone straight to `main`. Recorded in
`env-gotchas` with the recovery, alongside a second trap this retro walked into: **proving the new CI
step locally with its exact `git fetch --depth=1` SHALLOWED the working repository**, after which the
release commit reported no parent and `git status` invented a "behind 698". Both are cheap to notice
and expensive to miss.

**Two harness observations, both measured:**

- **The merge-gate mutation contract was flaky under load.** `deadline denies removed` survived once
  and was killed on retry. Diagnosed rather than re-run: the parse loop's budget and the
  post-network `past_deadline` share `PR_MERGE_GATE_DEADLINE`, so on a loaded machine the mutant
  still denied — from the *other* path — and a decision-only assertion could not tell them apart.
  Fixed by asserting the deny REASON (§7, change 3).
- **CI still has no retry for the Vitest worker-teardown race.** It hit #318 (`46 passed (46)`, every
  file at 100/100/100/100, `exit code 1`), green on re-run. `scripts/run_frontend_suites.sh` absorbs
  it in the pre-push gate but is deliberately gate-only, so the gate guarding the laptop is more
  robust than the gate guarding `main`. Filed as **#319**; not fixed here because it is a CI-workflow
  change with its own issue, and this PR must not grow to absorb it (rule 11's legitimate deferral).

- **No fix for #319 (CI has no retry for the Vitest teardown race).** It is a `deploy.yml` change

- **No fix for #326 (pool starvation).** Correctly deferred by the reviewer with the numbers
  attached; it needs 60 concurrent in-flight requests and the levers are pre-existing infrastructure
  (`pool_size`, `echo=True` hard-coded in prod).

  therefore *falsifies v1.13.0's bet that discipline would hold*. The reason v1.13.0 gave is still
  true — a hook cannot distinguish "discard my experiment" from "discard my fix", and it would fire
  on the single most common safe command in the loop. What changes is where the answer lives: it is
  now stated in the playbook and in §54 ("commit the round's fixes BEFORE the first mutation"), not
  only in a lesson nobody's charter points at. If it recurs again in v1.15, the next retro should
  price a `git stash push` wrapper instead of a deny.
- **Project 3's `Review rounds` field: keep the field, never publish from it.** The thread is the
  instrument (executable, re-derivable by anyone), and the field disagreed with the thread the last
  time it was filled. The token/time columns, by contrast, are now genuinely recorded and stay.

## 📌 Prediction (checkable at the v1.15 retro)

Stated as observables with the instrument named, because the last one was checked and one clause
failed:

1. **Zero merges whose newest canonical APPROVE predates a commit on the PR.** Instrument: replay
   each merged PR's thread as it stood at `mergedAt` through `pre-merge-gate.sh` (the exact script is
   in this retro's PR description). v1.14.0: **4 of 10**. The gate now denies this, so any occurrence
   means the gate was bypassed or the merge did not pass through it — and *that* is the finding.
2. **Zero PRs merged with no posted verdict at all.** v1.14.0: **1** (#321). No hook can enforce
   this; it is a charter-and-owner observable, which is exactly why it is worth measuring.
3. **Zero merged-result findings** — no Alembic head fork, no "green alone, broken by the merge".
   Instrument: `bash scripts/check_migration_heads.sh --against origin/main`, plus a read of every
   REQUEST CHANGES verdict for the phrase.
4. **Class-F (claim asserted rather than measured) blocker+major findings ≤ 2.** v1.14.0: 4;
   v1.13.0: 12. Same severity population, stated.
5. **Project 3 `Review rounds` filled for every issue the release ships** — or the column formally
   retired. v1.14.0 filled Tokens and Time for 8/8 and Review rounds for **0/8**; a half-filled
   telemetry row is how the v1.13.0 retro ended up publishing estimates.

**Falsification, stated up front.** Clauses 1 and 3 can both go to zero for the wrong reason: if
fewer merges pass through a guarded session at all, the gate is being routed around rather than
obeyed, and its coverage claim is void. So the next retro must first measure **merge provenance** —
`gh pr view <n> --json mergedBy` plus whether the PR's thread shows a delta-confirm — and report the
count of web-UI merges alongside clause 1. If any v1.15 PR is merged from the web UI, clause 1 is
reported as *unmeasured for that PR*, not as a pass. Second falsifier: if mean rounds rise back above
3.0 while classes F, G and S stay low, then the constraint has moved to material difficulty again and
the answer is not another charter paragraph.
